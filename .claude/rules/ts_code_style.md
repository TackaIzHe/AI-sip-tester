# Правила оформления TypeScript-кода

Свод правил по стилю кода, составленный по руководству
«Google TypeScript Style Guide» (русский перевод — `doc/codestyle.html`,
оригинал: https://google.github.io/styleguide/tsguide.html, версия от 21.10.2023).

Формулировки: «нельзя» / «обязательно» — ДОЛЖЕН/НЕ ДОЛЖЕН (строго),
«предпочтительно» / «не предпочтительно» — РЕКОМЕНДУЕТСЯ/НЕ РЕКОМЕНДУЕТСЯ,
«допустимо» — ВОЗМОЖНО (согласно RFC 2119).

## 1. Основы исходных файлов

- Кодировка файлов — UTF-8.
- Единственный допустимый пробельный символ (кроме перевода строки) — ASCII
  пробел `0x20`; табуляции в исходном коде запрещены, прочие пробелы в
  строковых литералах экранируются.
- Для символов, имеющих специальную экранирующую последовательность
  (апостроф, кавычка, обратный слеш, backspace, form-feed, перевод строки,
  табуляция и т.п.), использовать её, а не числовое экранирование
  (\\x0a, \\u000a, \\u{a}). Восьмеричные экранирования не использовать.
- Символы не из ASCII писать напрямую (например `μs`); шестнадцатеричное или
  unicode-экранирование (\\u221e) — только для непечатаемых символов и с
  пояснительным комментарием.

## 2. Форматирование блоков кода

Образец оформления блоков кода — `doc/primer.md` (имена идентификаторов в
нём условны и служат лишь для демонстрации переносов, значимо
форматирование).

- Максимальная длина строки — 90 символов. Строку, не помещающуюся в лимит,
  переносить по логическим границам: после запятых списков, перед бинарными
  операторами; голые переносы внутри произвольных мест строки нельзя.
- Отступ — 4 пробела на уровень вложенности; переносы выравниваются по
  элементу, к которому относятся (параметры — по первому параметру, см.
  ниже).
- Составной блок: открывающая `{` — на новой строке на уровне отступа
  конструкции, закрывающая `}` — на новой строке на том же уровне
  (`{`/`}` не писать в конце строки заголовка или условия):

  ```ts
  function handle_call(call_id: string)
  {
      if (is_registered)
      {
          send_invite(call_id);
      }
      else
      {
          send_reject(call_id);
      }
  }
  ```

- Ключевое слово `else` (а также `catch`/`finally`) — с новой строки после
  закрывающей `}` предыдущей ветки, форма `} else {` нельзя.
- Список параметров (аргументов), не помещающийся в 90 символов: по одному
  на строке, продолжения выровнены по первому параметру:

  ```ts
  function register_subscriber(subscriber_number: string,
                               subscriber_password: string,
                               pbx_host: string,
                               pbx_port: number): Promise<boolean>
  {
      ...
  }
  ```

- Тело из одного оператора допустимо писать без `{ }` — единственным
  оператором на новой строке с шагом отступа; составное тело — обязательно
  с `{ }`; если в какой-либо ветве `if`/`else` тело составное, `{ }`
  обязательны во всех ветвах этой конструкции.
- Логически самостоятельные операторы и блоки внутри тела разделять одной
  пустой строкой; пустые строки в начале и конце тела не дублировать
  (см. «Функции»).

## 3. Структура исходного файла

Порядок частей файла (разделять одной пустой строкой):

1. информация об авторских правах / лицензии (в JSDoc), при наличии;
2. JSDoc с `@fileoverview` (описание содержимого, применения, зависимостей), при наличии;
3. объявление импортов;
4. реализация.

### Импорты

- При импорте TS-кода всегда указывать путь; в пределах проекта предпочтительны
  относительные импорты (`./foo`, `../parent/file`); ограничивать количество
  родительских шагов (`../../../`).
- Именованные импорты (`import {Foo} from './foo'`) — для часто используемых
  элементов с понятными именами; импорты пространств имён
  (`import * as tableview from './tableview'`) — для множества элементов
  больших API. Не выстраивать длинные списки переименованных имён в одном
  именованном импорте — взять модуль целиком.
- Переименование через `as` — при коллизиях имён, генерируемых именах или
  неясных именах импортируемых элементов (например `from` → `observable_from`).
- Импорт по умолчанию — только для поддержки стороннего кода, который его
  требует; импорт побочных эффектов — только `import '...';`.
- Если элемент используется только как тип — `import type {Foo} from './foo'`;
  для значений — обычный импорт.

### Экспорты

- Использовать только именованные экспорты: `export class Foo {}`,
  `export function bar() {}`.
- Экспорт по умолчанию (`export default`) нельзя: у него нет канонического
  имени, импорты расходятся, ошибки опечаток не ловятся.
- Экспортировать только то, что реально используется вне модуля —
  минимизировать публичную API-поверхность.
- `export let` нельзя (мутабельные экспорты непредсказуемы при реэкспорте).
  Для наружно-мутабельного состояния — приватная переменная и экспорт
  функции-геттера; для выбора значения по условию — сначала вычисление, затем
  `export const SOME_API = pick_api();`.
- Не создавать классы-контейнеры со статическими полями/методами «ради
  пространства имён» — экспортировать константы и функции отдельно.
- Типы реэкспортировать через `export type {AnInterface} from './foo';`.

### Модули вместо пространств имён

- Конструкции `namespace Foo { ... }` запрещены (разделение — отдельными
  файлами; исключение — вынужденное взаимодействие с внешним сторонним кодом).
- Запрещены `/// <reference path="..."/>` и `import x = require('...')` —
  только синтаксис модулей ES6.

## 4. Языковые особенности

### Локальные переменные

- Объявлять только через `const` (по умолчанию) или `let` (при переназначении);
  `var` нельзя. Переменные нельзя использовать до объявления.
- Одна переменная на объявление: `let a = 1, b = 2` — нельзя.

### Массивы и объекты

- Конструкторы `Array()` и `Object()` (с `new` и без) запрещены; литералы
  `[]` и `{}`. Для массива заданного размера — `c.length = n` или
  `Array.from({length: n})`.
- Нечисловые свойства массива (кроме `length`) не определять — использовать
  `Map` или `Object`.
- Spread (`[...foo]`, `{...bar}`) — только для совместимых значений: в массив
  раскладывать итерируемое, в объект — объекты; не раскладывать примитивы,
  `null`/`undefined` и объекты с прототипом, отличным от `Object`
  (экземпляры классов).
- Деструктуризация допустима; у необязательного деструктурируемого параметра
  значение по умолчанию — `= []` / `= {}`, а значения по умолчанию полей —
  в левой части: `function f({num, str = 'default'}: Options = {}) {}`
  (нельзя `({num, str}: Options = {num: 42, str: 'default'})`).
  Для упаковки/распаковки нескольких значений предпочитать деструктуризацию
  объекта, а не массива.
- Для итерации по объектам — `for (const x of Object.keys(obj))` /
  `Object.entries(obj)`, либо `for..in` с фильтром `hasOwnProperty`;
  неффильтрованный `for..in` по объекту и любой `for..in` по массиву запрещены.
- Вычисляемые имена свойств литералов — в кавычках, в стиле ключей словаря
  (кроме `[Symbol.iterator]` и т.п. symbol-ключей).

### Классы

- Объявление класса не завершать точкой с запятой; выражение с классом
  (`export const Baz = class extends Bar {...}`) — завершать.
- Методы не разделять `;`; отделять друг от друга одной пустой строкой;
  конструктор отделять пустой строкой сверху и снизу.
- `toString` переопределять можно: всегда успешный, без побочных эффектов,
  без вызова других методов (риск бесконечного цикла).
- Приватные статические методы — предпочитать локальные функции модуля;
  статические методы вызывать только в том классе, где они определены;
  `this` в статическом контексте использовать нельзя.
- Конструктор всегда со скобками: `new Foo()`. Пустой конструктор или конструктор,
  просто делегирующий `super`, не писать; но конструкторы с параметризованными
  свойствами, модификаторами или декораторами параметров оставлять.
- Приватные поля `#ident` запрещены — использовать модификатор `private`.
- Свойства, никогда не переназначаемые вне конструктора, помечать `readonly`;
  очевидное присваивание параметра полю заменять параметризованным свойством
  (`constructor(private readonly bar_service: BarService) {}`); поля
  инициализировать при объявлении, а не в конструкторе. После конструктора
  свойства экземпляру не добавлять и не удалять; необязательные поля явно
  инициализировать `undefined`.
- Свойства, используемые вне лексической области класса (шаблоны фреймворков),
  — `protected`/`public`, не `private`; обходить видимость через `obj['foo']`
  нельзя.
- Геттеры — чистые (без изменения наблюдаемого состояния); сквозные аксессоры
  без логики не определять — свойство делать публичным (или `readonly`);
  скрытое за аксессором поле помечать словом `internal`/`wrapped`;
  `Object.defineProperty` для аксессоров не использовать.
- Вычисляемые свойства в классах — только типа `symbol`.
- Видимость ограничивать максимально; модификатор `public` не писать
  (допустим только для не-`readonly` параметризованных свойств конструктора).
- С прототипами напрямую не работать, миксины и модификация прототипов
  встроенных объектов запрещены (исключение — код фреймворков).

### Функции

- Именованные функции — объявлениями (`function foo() {}`), а не
  `const foo = () => ...`; стрелочная допустима, когда нужно явное указание
  типа (`const foo_search: SearchFunction = (a, b) => {...}`).
- Функциональные выражения (`function () {}` как значение/аргумент) запрещены —
  стрелочные; исключение: динамическая перепривязка `this` (не приветствуется)
  и генераторы.
- Вложенные в методы функции — предпочтительно стрелочные (доступ к внешнему `this`).
- Краткое тело стрелочной — только когда возвращаемое значение используется;
  иначе блочное тело (или `void expr`).
- `this` — только в конструкторах, методах, функциях с явным типом `this` и
  стрелочных в соответствующей области; не использовать `this` как ссылку на
  глобальный объект/контекст eval/цель события; перепривязку `this` делать
  стрелочными, а не `bind`/`const self = this`.
- В callback передавать стрелочную обёртку с явной передачей параметров
  (`['11','5'].map((n) => parseInt(n))`), а не именованную функцию напрямую —
  лишние аргументы могут пройти типизацию и испортить логику.
- Стрелочные функции как свойства классов обычно не использовать; вызывать
  методы экземпляра через стрелочную обёртку в месте вызова
  (`() => { this.listener(x); }`). Исключение — обработчики, которые нужно
  удалять: там свойство-стрелочная даёт постоянную ссылку; `bind` при
  навешивании удаляемых обработчиков запрещён.
- Значения параметров по умолчанию — без побочных эффектов, простые;
  при многих непозиционных необязательных параметрах предпочтительна
  деструктуризация объекта-параметра.
- Вместо `arguments` — rest-параметр; локальную переменную `arguments` не
  называть; вместо `Function.prototype.apply` — spread.
- Пустые строки в начале/конце тела функции запрещены; логические группы —
  одна пустая строка. В генераторах: `function* foo()`, `yield* iter`.
  После `...` пробел не ставить.

### Литералы и преобразования

- Строковые литералы — в одинарных кавычках; перенос строки обратным слешем
  внутри литерала запрещён (длинные строки — конкатенация или шаблон).
  Сложную конкатенацию и многострочные строки — шаблонными литералами (`` ` ``).
- Числовые литералы: префиксы `0x`, `0o`, `0b` строчными; ведущий ноль без
  `x/o/b` нельзя.
- Преобразование типов: `String()`, `Boolean()` (без `new`), шаблонные
  литералы, `!!`. Enum (в т.ч. объединения с ним) к boolean не приводить —
  сравнивать явно (`level !== SupportLevel.NONE`).
- К строке не приводить конкатенацией; для парсинга чисел — `Number()`
  с явной проверкой `NaN`/`isFinite`; `parseInt`/`parseFloat` — только для
  недесятичных оснований и с предварительной валидацией входной строки
  регуляркой; унарный `+` для приведения к числу запрещён.
- В условиях `if`/`for`/`while` не делать явного `!!` — уже есть неявное
  булево преобразование.

### Управляющие структуры

- `if`/`else`/`for`/`do`/`while` — составное тело всегда с `{ }` (скобки с
  новой строки, см. §2 «Форматирование блоков кода»); одиночный оператор
  допустим без скобок — на новой строке с шагом отступа либо конструкцией,
  целиком умещающейся в одну строку.
- Присваивания внутри условий избегать; если необходимо — удваивать скобки
  (`while ((x = f()))`).
- По массивам — `for (const x of arr)` (или обычный `for` с индексом,
  `arr.entries()`); `for..in` только для объектов со словарными ключами и
  с `hasOwnProperty` (лучше `Object.keys/values/entries`).
- Необязательные группирующие скобки опускать только когда код точно не будет
  понят неверно; лишние скобки после `delete`, `typeof`, `void`, `return`,
  `throw`, `case`, `in`, `of`, `yield` не ставить.
- Исключения — обычный способ обработки ошибок (не «специальные» возвраты
  объектов-ошибок). Создавать только `new Error(...)`; бросать и передавать в
  `Promise.reject` только экземпляры `Error` или подклассов (иначе нет
  трассировки стека). В `catch (e: unknown)` относиться к `e` как к `Error`
  (сужать через `instanceof`), не защищаться избыточно. Пустой `catch` —
  только с комментарием-обоснованием.
- Блок `try` держать минимальным: в него — только вызов, способный бросить
  (допустимо расширить try на весь цикл ради производительности).
- `switch` — обязательно с последним `default:` (даже пустым); непустые группы
  `case` завершать `break`/`return`/`throw`, fallthrough непустых групп
  запрещён (пустые — можно объединять).
- Равенство — только `===`/`!==`; исключение: `== null` / `!= null` для
  совместного охвата `null` и `undefined`.
- Утверждения типа (`x as Foo`) и ненулевого значения (`y!`) небезопасны —
  не использовать без явной или объяснимой причины; предпочитать рантайм-проверку
  (`instanceof`, проверка на null); при необходимости — комментарий, почему
  это безопасно. Синтаксис только `as` (не `<Foo>z`); двойное утверждение —
  через `unknown` (`x as unknown as Foo`). Для объектных литералов тип задавать
  аннотацией (`const foo: Foo = {...}`), а не `as Foo`.
- Новые декораторы не определять; использовать только данные фреймворком.
  Декоратор ставится непосредственно перед элементом, без пустой строки после
  него; JSDoc — перед декоратором.

### Запрещённые возможности

- Классы-обертки примитивов как конструкторы (`new String(...)`, `new Boolean(...)`,
  `new Number(...)`) — нельзя (вызов без `new` для приведения — можно).
- Полагаться на автоматическую вставку точки с запятой (ASI) нельзя —
  завершать все операторы точкой с запятой явно.
- `const enum` нельзя — обычный `enum`.
- `debugger` в рабочий код не включать.
- `with` нельзя.
- `eval` и `new Function(...string)` нельзя (кроме загрузчиков кода).
- Нестандартные/устаревшие/незавершённые (черновики TC39, WHATWG) и
  проприетарные возможности ECMAScript и Web-платформы не использовать;
  только функционал текущей спецификации ECMA-262 (проекты под конкретную
  среду — Chrome/Node/Electron — могут использовать её API).
- Встроенные типы не расширять методами (конструкторы/прототипы) и не
  зависеть от библиотек, которые это делают; символы в глобальный объект не
  добавлять без крайней необходимости.

## 5. Именование

Идентификаторы — только ASCII буквы, цифры и `_` как разделитель слов.

Именование — в `snake_case` (с заглавными буквами только там, где указано):

| Стиль | Категория |
|---|---|
| `UpperCamelCase` | класс / интерфейс / тип / enum / декоратор / параметр типа / компонент TSX |
| `snake_case` | переменная / параметр / функция / метод / свойство / файл / импорт модуля |
| `UPPER_SNAKE_CASE` | глобальные константы уровня модуля и значения enum |
| `#ident` | не используется |

- Всё, что именуется (кроме типов/классов и констант, см. таблицу), —
  `snake_case`: `load_http_url`, `dns_connection_index`, `customer_id`,
  `sip_port`. Файлы — тоже `snake_case` (`sip_pool.ts`).
- Имена — описательные и понятные новым читателям; аббревиатуры, известные
  только команде, и «вырезание» букв запрещены; венгерская нотация запрещена.
  Однобуквенные имена допустимы для области видимости ≤ 10 строк, не в
  экспортируемом API.
- Акронимы вести как отдельные слова с `_`: `load_http_url`, `sip_port`
  (не `loadHTTPUrl`, не `sipPORT`; исключение — заимствованные имена
  платформы, например `XMLHttpRequest`, в именах типов).
- `_` в начале/конце идентификатора (для «приватности» или «неиспользуемого
  параметра») запрещён — `_` только разделитель слов внутри имени;
  неиспользуемые элементы при деструктуризации пропускать запятыми:
  `const [a, , b] = ...`.
- Не дублировать в имени то, что уже в типе: не подчёркивать приватность,
  не префиксить `opt_`, не помечать интерфейсы как `IMyInterface` (имя
  интерфейса к классу должно выражать причину его существования:
  `class TodoItem` + `interface TodoItemStorage`).
- `$` в именах не использовать, кроме соглашений сторонних фреймворков
  (напр. суффикс `$` у Observable — по согласованному в проекте решению).
- `UPPER_SNAKE_CASE` — только для сущностей уровня модуля и значений enum
  (в т.ч. `static readonly` поля уровня модуля); создаваемые в рантайме более
  одного раза — `snake_case`. Стиль `UPPER_SNAKE_CASE` сигнализирует
  «не изменять», даже если технически значение мутабельно.
- Импорты пространств имён — `snake_case`, как имя файла
  (`import * as sip_pool from './sip_pool'`).
- Тестовые методы xUnit-подобных фреймворков именовать с `_`-разделителями:
  `test_x_when_y_does_z()`.
- Параметры типа: одна заглавная (`T`) или `UpperCamelCase`.
- Псевдонимы сохраняют стиль и имя оригинала; для переменных-псевдонимов —
  `const`, для полей класса — `readonly`.

## 6. Система типов

- Полагаться на вывод типа; не аннотировать тривиально выводимое
  (`const x: boolean = true` — плохо; `new Set()` аннотировать не нужно).
  Явно указывать тип, где иначе дженерик выведется в `unknown`
  (`new Set<string>()`), и для сложных цепочек, где аннотация улучшает
  читаемость (`const value: string[] = await rpc.get_some_value().transform()`).
- Аннотация возвращаемого типа — по усмотрению автора; рецензент может
  потребовать её для сложных типов; локальная политика проекта может
  требовать всегда.
- `undefined`/`null` оба допустимы — выбор по контексту API; специального
  синтаксиса нет — union (`string|null`).
- Для необязательных параметров/полей — `?:`, а не `|undefined` в типе;
  в классах предпочитать инициализацию полей.
- Типизация структурная: при предоставлении реализации под интерфейс — явная
  аннотация (`const foo: Foo = {...}`), чтобы ошибка возникала на объявлении,
  а не в месте использования. Структурные типы описывать интерфейсами,
  не классами.
- Для описания объекта — `interface`, а не `type` = объектный литерал.
- Массивы: `T[]` / `readonly T[]` для простых `T` (буквенно-цифровые и точка)
  и многомерных простых; `Array<T>` / `ReadonlyArray<T>` для составных
  (объектные литералы, unions); правила применяются на каждом уровне вложенности.
- Словари: индексная сигнатура с осмысленным именем ключа —
  `{[user_name: string]: number}` (не `{[key: string]: ...}`);
  рассмотреть `Map`/`Set`; при статически известном наборе ключей — `Record<Keys, T>`.
- Mapped/conditional типы и операции над типами (`Pick`, `Partial`, ...) —
  использовать самую простую выразимую конструкцию; небольшое дублирование
  `interface`-ами дешевле сложных выражений (расширение интерфейса обычно
  проще `Pick`).
- `any` опасен — не использовать; альтернативы: более конкретный тип
  (интерфейс, встраиваемый объектный тип, псевдоним, дженерик), `unknown`
  (с сужением через type guards), либо подавление предупреждения линтера с
  комментарием-обоснованием (моки в тестах).
- Тип `{}` не использовать; вместо него `unknown`, `Record<string, T>` или
  `object`.
- Для «пар» — кортеж (`[string, string]`), но при необходимости имён полей —
  встраиваемый объектный тип (`{host: string, port: number}`) вместо
  интерфейса `Pair`.
- Обёрточные типы `String`, `Boolean`, `Number`, `Object` в аннотациях не
  использовать — только строчные `string`, `boolean`, `number`; вместо
  `Object` — `object` (или `Record<...>` для словарей). Вызывать обёртки как
  конструкторы (`new String(...)` и т.п.) нельзя.
- Избегать API, у которых возвращаемый тип представлен только дженериком
  (`function parseYAML<T>(s: string): T` выводится в `any`); при работе с
  такими — всегда явно указывать аргумент дженерика.

## 7. Требования к цепочке инструментов

- Все файлы должны проходить проверку типов компилятором TypeScript
  (`npm run build`).
- `@ts-ignore`, `@ts-nocheck` запрещены. `@ts-expect-error` — не следует;
  допустим лишь в юнит-тестах, предпочитая ему локальное приведение типа с
  комментарием или подавление линтера с обоснованием.

## 8. Комментарии и документация

- Для документации — JSDoc `/** ... */`; для комментариев реализации —
  строчные `// ...`.
- Многострочные комментарии — несколько `//`-строк с отступом уровня кода;
  блочный `/* */` для обычных комментариев и рамки из символов — нельзя.
- JSDoc: многострочная форма с `*` на каждой строке или однострочная
  `/** Краткое описание. */`; содержимое — в формате Markdown (списки — через
  `-`, иначе инструмент склеит строки).
- JSDoc-теги: каждый тег с отдельной строки, в начале строки; переносы текста
  тега — с отступом 4 пробела (верстка по описанию не обязательна); в тегах
  `@desc`/`@fileoverview` переносы без отступа.
- Документировать JSDoc все экспорты верхнего уровня и все свойства/методы,
  назначение которых не очевидно из имени (кроме экспортов только для
  инструментов, например `@NgModule`).
- Описание класса — достаточное для понимания как/когда его использовать;
  описание метода — глагольное сочетание в третьем лице («Возвращает…»,
  а не «Верни»); описания параметров/возвращаемого значения опускать, когда
  они очевидны из сигнатуры.
- Не повторять в комментарии имя и тип элемента (`@param foo_bar_service Сервис fooBar` —
  пусто); `@param`/`@return` только когда добавляют информацию.
- Аннотации типов в JSDoc избыточны в TS: не писать типы в `@param`/`@return`,
  не дублировать `implements`/`enum`/`private`/`override` тегами.
- Параметризованные свойства документовать `@param` в JSDoc конструктора.
- При вызове функции, где имя метода и значение не передают смысл параметра,
  — комментарий «имя параметра»:
  `some_function(obvious_param, /* should_render= */ true, /* name= */ 'hello')`
  (в существующем коде допустим старый стиль `true /* should_render */`,
  если он уже применяется в файле). До этого — подумать о рефакторинге
  на интерфейс с деструктуризацией.
- JSDoc размещать до декораторов, не между декоратором и элементом.
- Устаревшие элементы помечать `@deprecated` с ясным указанием, как исправить
  места вызова.

## 9. Политики

- Не урегулированное специфики — делать как в текущем файле, затем — как в
  соседних файлах каталога (единообразие).
- Новые файлы — по этому руководству; при правках чужого файла нового кода —
  не нарушать руководство, но по возможности сначала переформатировать файл
  отдельно от содержательной правки. Массовое переформатирование не должно
  мешать ревью основного кода.
- Сгенерированный код стилю не обязан следовать, кроме идентификаторов, на
  которые ссылается ручной код (в них допустимы `_`).
- При двух эквивалентных вариантах выбирать один — во избежание расхождений
  без причины.

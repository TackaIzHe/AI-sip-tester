# Правила комментирования кода в проекте

Свод фактически сложившихся в проекте соглашений по комментариям (по коду
`server/`, корневых `bridge_main.ts`/`e2e_runner.ts`, `tests/`, `doc/.probe_*.ts`,
`public/index.html`). Дополняет §8 свода `.claude/rules/ts_code_style.md`, не
дублирует его; для специфики проекта этот файл — локальная политика свода
(§9 «Политики»). Формулировки «нельзя»/«обязательно» — ДОЛЖЕН/НЕ ДОЛЖЕН,
«предпочтительно»/«допустимо» — РЕКОМЕНДУЕТСЯ/ВОЗМОЖНО (RFC 2119).

## 1. Общие нормы

- Язык комментариев — русский. Термины SIP (REGISTER, INVITE, Call-ID, rport),
  имена файлов/идентификаторов, ссылки на пункты плана остаются латиницей:
  `// rport в Via обязателен (иначе REGISTER с эфемерного порта теряется)`.
- Комментарий объясняет WHY, а не WHAT: причину решения, ограничение протокола,
  проверенное поведение станции, следствие нарушения. Пересказ кода словами
  нельзя (`// закрываем сокет` над `close()` — пусто).
- Ссылка на первоисточник обязательна там, где комментарий утверждает факт:
  `(plan_2.md п.4)`, `(doc/sip_rfc.md §5.10)`, `(doc/task_8_plan_2.md)`,
  `как на стенде`, `из прогона-зонда doc/.probe_e2e8.ts`.
- Связи между файлами — словами `related:` (строка заголовка) и `см.` внутри
  комментариев: `// related: server/sip_pool.ts (PoolError), server/app.ts`.
- Типографика: кавычки-«ёлочки», тире «—», многоточие в логах шага «…».

## 2. Заголовок файла

- Каждый `.ts`-файл ОБЯЗАН начинаться с заголовочного блока строк `//` до
  импортов; JSDoc-`@fileoverview` в проекте НЕ используется — его роль играет
  этот блок (`@author`/`@license` тоже не пишутся).
- Структура заголовка (части разделяются пустой строкой-комментарием `//`):
  1. что это, ссылка на пункт плана и/или источник переноса (`task2/...`);
  2. ключевые контракты, инварианты и проверенное поведение станции
    (список через `-` — когда пунктов несколько);
  3. последняя строка — `// related: <файлы и документы>` (перечисляется
    через запятую, при необходимости с уточнением в скобках).
- Образцы (как есть в коде):

  ```ts
  // Логирование HTTP-запросов (plan_2.md п.5.1): одна строка на запрос —
  // метод, путь, код ответа, длительность. Работает по событию 'finish',
  // чтобы видеть итоговый код и после контроллеров, и после error_handler.
  // related: server/app.ts (подключение), middleware/error_handler.ts.
  ```

  ```ts
  // Журнал SIP-событий и генерация отчётов (plan_2.md п.3).
  //
  // Источники событий (п.3.1):
  //  - attach_phone      — снапшоты стейт-машины (server/sip/state.ts);
  //  - attach_transport  — события транспорта (server/sip/transport.ts: incoming,
  //                        ringing, established, terminated, …);
  //  ...
  ```

- HTML-страница (`public/index.html`) — заголовок `<!-- ... -->` с описанием
  панелей и используемых endpoint-ов; JS-клиент страницы — свой `//`-заголовок
  с ролью («чистый наблюдатель: только GET на rails-style API сервера»).
- Зонды `doc/.probe_*.ts` — в заголовке ОБЯЗАНЫ указывать статус и запуск:
  `// Прогон-зонд для фиксации ассертов plan_2.md п.8 (не тест, не в бандле):`
  `//   npx tsx doc/.probe_e2e8.ts`.

## 3. JSDoc экспортов и членов

- Каждый экспорт верхнего уровня (class/interface/type/const/function)
  документается JSDoc.
- Форма JSDoc — ТОЛЬКО многрочная: `/**` и `*/` каждое на своей строке,
  текст с ` *` на каждой строке; однострочная форма `/** … */` нельзя —
  это сужение разрешения §8 свода (однострочная форма «допустима») до строгой
  нормы: локальная политика проекта по §9 свода. Распространяется на все
  JSDoc-комментарии без исключений: экспорты, методы, геттеры, private-поля,
  пустые описания-заглушки.

  ```ts
  /**
   * Подписчик на изменения снапшота.
   */
  export type Listener = (s: PhoneSnapshot) => void;

  /**
   * Смена состояния; возвращает false, если переход запрещён.
   */
  set(next: PhoneState, patch: Partial<Omit<PhoneSnapshot, 'state'>> = {}): boolean
  ```

  ```ts
  /**
   * Машина состояний телефона: хранит PhoneSnapshot, отсекает запрещённые
   * переходы и уведомляет подписчиков. Используется и в сессиях моста
   * (server/sip/session.ts), и в пуле виртуальных абонентов (server/sip_pool.ts) —
   * отсюда 1:1 состояний протокола v:1.
   */
  export class PhoneStateMachine
  ```

- Методы, геттеры и private-поля, назначение которых не очевидно из имени,
  документируются тем же способом; поля с неочевидным жизненным циклом —
  обязательно:

  ```ts
  /**
   * Итог последней регистрации — нужен, напр., мосту для события error{code}.
   */
  last_reg?: RegResult;
  ```
- `@param`/`@return` — только когда добавляют информацию: семантика
  флага/колбэка, побочные эффекты, значения по умолчанию, непонятные из имени.
  Тип в теге не писать; параметр описывать через `—`, флаги — перечислением
  значений (как есть в коде):

  ```ts
  /**
   * @param on_trace — необязательный наблюдатель сырых SIP-сообщений для
   * журнала автотестов (plan_2.md п.3.1); навешивается на сокет в connect().
   */
  ```

  ```ts
   * @param report false — фоновая сессия (второй входящий в занятого): её
   * завершение не транслируем стейт-машине телефона, только убираем за собой.
   */
  ```

- Комментарий над конструктором с параметризованными свойствами — `@param` на
  каждое такое свойство (§8 свода), остальные параметры — только значимые.

## 4. Строчные комментарии `//` в теле

- Размещение — над комментируемым кодом. Короткое пояснение к одному
  оператору допустимо в конце строки после `;`:
  `update_del_state(); // после перерисовки чекбоксов новые — кнопка гаснет`.
- Типовое содержимое (обязательно с указанием источника/последствия):
  - грабли и ограничения — с формой «иначе …»:
    `// Порт 9 (discard) + inactive: кодек согласуется (иначе АТС отвечает 488),`;
  - проверенное поведение живой станции:
    `// Challenge опционален: стенд отвечает REGISTER→200 без Digest (см. шапку).`;
  - дефекты-регрессии из task2 — маркер `BUG-N` на месте обхода/ фикса:
    `this.locally_cancelled = true; // BUG-5: свой отбой не должен оставлять «487»`;
  - отсылки к протокольной справке:
    `// Полная таблица кодов — doc/sip_rfc.md §7.2, разбор ключевых — §7.3.`.
- Пустой `catch`/ветка-заглушка — `/* noop */` (комментарий-обоснование по
  §8 свода), иных блочных `/* */`-комментариев в TS-коде не быть должно.
- Закоммеченный код нельзя (в проекте не встречается); временный код — удалять,
  историю хранит git.

## 5. Разделители логических секций

- Внутри длинных файлов секции отделяются баннером
  `// ---------- имя секции ----------` (с отступом уровня кода внутри
  класса; ссылка на пункт плана — уместна):

  ```ts
  // ---------- разбор сырых SIP-сообщений ----------
  ```

- В `public/index.html` те же баннеры в синтаксисе места: CSS —
  `/* ---------- статус-строка ---------- */`, разметка — `<!-- Панель
  «Файлы»: дерево (слева) + содержимое (справа). -->`, JS —
  `// ---------- панель «Отчёты» (п.6.1) ----------`.

## 6. Тесты и раннер

- Имена `describe`/`it`/`test` — на русском, формулировка проверяемого
  поведения (что обязана делать станция/код), SIP-термины латиницей:
  `it('повторный register идемпотентен: без нового транспорта и REGISTER', …)`,
  `it('200 — абоненты конфига с флагом can_register (3203 — false)', …)`.
- Заголовок тестового файла — по §2: что тестируется, гард переноса/критерий,
  нужен ли стенд и команда запуска, `related:`. Образец:

  ```ts
  // Юнит-тесты таблицы переходов PhoneStateMachine (server/sip/state.ts) —
  // перенос task2/tests/state.test.ts: запрещённые переходы отсекаются, поля
  // снапшота (peer/error/timer) живут по состоянию. Гард переноса (plan_2.md §2,
  // критерий): менять переходы можно только здесь. Стенд не нужен — чистая
  // логика, нод-независимая. Запуск: npm run test:unit.
  ```

- Внутренние комментарии теста — только к неочевидным ассертам, со ссылкой на
  источник ожидания: `// Ассерт «входящий у 52, не у 3203» — из прогона-зонда …`.
- Шаги e2e-раннера (`ctx.step`) — русские описания протокольного действия с
  кодами/номерами: `ctx.step('положил трубку вызывающий (BYE)…')`.

## 7. Плотность комментариев

- Сложные модули (стейт-машина, транспорты, пул, раннер, журнал) — плотные
  заголовки и комментарии-инварианты у каждого неочевидного решения
  ( ориентир — до ~20 % строк); простые (тонкие контроллеры, константы) —
  заголовок + JSDoc экспортов, без пересказа кода.
- Правило проверки: читатель без контекста сессии должен по комментариям
  понять, почему код именно такой и что сломается при правке («иначе …»).

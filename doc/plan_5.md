# План 5: кейс B — `ss_info.c : ss_on_rx_notify()` (event-list / SSW_SRVM): почему станция в него не заходит

## Context

Запись `doc/task_22_plan_2.md` (генератор стимулов T1–T8) и её первоисточник
`doc/los_mem/res.md`, кейс **🥈 B**: станция `pa_sip` обрабатывает входящий
NOTIFY пакета `event-list` (SSW_SRVM, distinctive_ring) в
`ss_info.c : ss_on_rx_notify()`; на фиксированный буфер свойства (лимит 32
байта) приходят value len 137–139 и name len 33
(`replace_category_from_redirection`) — кандидаты утечки по error-пути. Цель —
довести наш стимул так, чтобы станция РЕАЛЬНО заходила в эту логику
(маркерные строки в её логе).

**Новые логи:** `doc/los_mem/act_log.157.log` (снят 2026-11-06 после приёмки
t1..t8 из `doc/task_26_plan_2.md`; 10 001 строка; концы дампа — `Trace APP:
level 0` / `pa-pjsip>`, т.е. это трассировка консоли pa-pjsip, её фильтр может
отличаться от старых `pbx_sip*.log`). Часы станции отстают от наших ~34 мин
(интервал дампа 18:18–18:26 по станции ≈ 18:53–19:00 реальных прогонов).

**Что видно по новому логу (факты):**
- маркеров кейса B — НОЛЬ: `ss_info.c` / `ss_on_rx_notify` / `bad property` /
  `event-list` / `notify` (регистронезависимо) не встречаются вовсе;
- в СТАРЫХ логах кейс B live-подтверждён: `traces_max_load/traces/pbx_siperr.log`
  ×9, `pbx_sip.1.log` ×11, `traces_normal_load/traces(6)/pbx_siperr.log` ×4,
  `traces 20260824/pbx_sip.1.log` ×2 и др.;
- подписку SSW_SRVM станция заводит САМА, как UAC, на нас:
  `R-URI sip:u00s29p00@192.168.80.159:5060`, `From/Contact
  sip:u00s29p00@192.168.80.133:5060` (signalling-IP адаптера, trunk 02,
  expires 7200);
- вне прогонов стимула наш `SipStation` отвечает на этот SUBSCRIBE **405**
  (штатная мимикрия plan_4) → `Subscription state SENT → TERMINATED`,
  `subscribe-status … cause 405`, подписка умирает;
- во время прогонов движок забирает SUBSCRIBE себе (hook из task_26):
  `ACCEPTED` (cause 200) — 6 штук; ещё 3 эпизода `cause 408` (ответ не дошёл);
- НИ ОДНОГО принятого NOTIFY в дампе нет → NOTIFY с «плохими свойствами» на
  станцию не приходили никогда → `ss_on_rx_notify` не вызывался — кейс B не
  достигается НЕ станцией, а НАШИМ генератором.

**Дамп №2: `doc/los_mem/act_log_2.157.log` (снят 2026-11-09 ~10:00, 5385
строк; часы станции 09:55:27–09:57:24 — почти реальное время, прежний разнос
~34 мин не наблюдался; хвост — `trace app on 0`). Факты:**
- ПЕРВЫЕ NOTIFY дошли до станции НАМИ: 90 штук (cseq 3..92, ~1/с, с
  09:56:01.548 по 09:57:00.974 — профиль короткого прогона t2/t8),
  `mod_pa_transit_ab` видит их «request from trunk!» (ab 52) — доставка на
  .157:5060 работает;
- все 90 получили от `sip_endpoint.c` **500 «Unknown method: NOTIFY»**
  (`Response msg 500/NOTIFY` ×90) — у endpoint станции обработчик метода
  NOTIFY в этот момент НЕ зарегистрирован; маркеры кейса B (`ss_info.c` /
  `ss_on_rx_notify` / `bad property` / `event-list`) снова НОЛЬ;
- за каждый 500 станция печатает `fail2ban: BAN suggest:
  192.168.80.159:5060 (Unknown method: NOTIFY)` ×90 — риск забанить стенд,
  учитывать при экспериментах п.3;
- наш SUBSCRIBE (с .159, `caller 9404`, `callee 52`, `contact 9404`,
  expires 600) станция теперь ПРИНИМАЕТ как BLF: `sub_alloc: BLF sub 291b`,
  UAS-диалог + mod-evsub (прежних 489/401→403 из task_22 нет); NOTIFY через
  21 мс после неё — тот же 500 «Unknown method»;
- собственных SSW-подписок станции (UAC) в дампе нет (`sub_create_uac` = 0);
  активность станции к .159 — REGISTER-и trunk 34
  (`u00s34p00..p03@192.168.80.159:5060`,
  Contact `…@192.168.80.157:5060;extensions="answermode"`), наш SipStation
  отвечает им мимикрией (не OPTIONS → 405);
- внутренний телефон .83.84 активно подписывается (BLF 9404→1197, 17
  SUBSCRIBE с Digest 401→403) — фон не мешает;
- исходящих NOTIFY станция не слала; `subscribe-status` из PBX-ядра ×19.

**Вердикты по гипотезам по дампу №2 (дополняют п.1–3):**
- **H1 — закрыта на транспорте:** пакеты доходят до .157 и опознаны «from
  trunk»; но вопрос адресата остаётся в силе для ДРУГОГО направления — NOTIFY
  должен приходить станции в её СОБСТВЕНной подписке на её Contact;
- **H2 — основной вариант, уточнена:** `ss_on_rx_notify` — обработчик
  входящих NOTIFY подписки, которую станция завела САМА (SSW SRVM, пир —
  notifier); вне такой живой подписки обработчик не зарегистрирован и любой
  NOTIFY («в пустоту», или в UAS-подписку, где станция — notifier, а не
  подписчик) → 500 «Unknown method». Отсюда цепочка входа в кейс B:
  наш сервер принимает SUBSCRIBE станции (200 + Contact) → мы notifier →
  шлём event-list NOTIFY «с плохими свойствами» в её Contact → обработчик
  вызывается;
- **H3 — закрыта:** «NOTIFY 500×N» в сводках — реальные ответы станции
  (`created`+`Destroying txdata`+fail2ban-строки), не наша петля; сводки
  пересчитывать честно по прежнему плану;
- **H4 — практически закрыта:** тот же level 0 исправно пишет RX NOTIFY
  (`Processing incoming message: Request msg NOTIFY`) — отсутствие маркеров
  в дампе №1 объяснялось отсутствием трафика, а не фильтром.

**Рабочие гипотезы (проверяются по порядку п.1–3):**
- **H1 — адресат:** event-list NOTIFY уходит на `target` (.157:5060) вместо
  Contact подписчика из SUBSCRIBE (`192.168.80.133:5060`); на .157 диалога нет.
- **H2 — чужой диалог:** NOTIFY генерируется в «своих» UAC-диалогах
  генератора (его SUBSCRIBE станция отвергла 489/403), а не в ПРИНЯТОЙ
  подписке станции (Call-ID/To-tag из её SUBSCRIBE и нашего 200).
- **H3 — петля 500:** «NOTIFY 500×N» в сводках t1/t2/t8 — ответы НАШИХ же
  клиентов на СВОИ NOTIFY: датagram уходит с :5060 на .157, но часть
  доходит/зацикливается локально (хук скармливает весь UDP-вход своим
  клиентам, клиент и отвечает себе 500); на станции этих NOTIFY не было.
- **H4 — лог-фильтр:** NOTIFY приходили, но новый act_log (level 0) их не
  пишет, в отличие от старых pbx_siperr.log — проверить повторным снятием
  трассы с тем же уровнем, что давал маркерные строки в старых дампах.

## Объём

- Диагностика «почему не заходим в кейс B» по новым/старым логам + сырому
  журналу генератора; правки стимула/станции, чтобы станции приходил
  корректно сформированный event-list NOTIFY в принятой подписке.
- Конфигурация BLF/SSW на самой АТС (номера генератора) — вне объёма: подписка
  SSW_SRVM на `u00s29p00` у пира уже есть, её и используем.
- Приёмка — маркерные строки `ss_info.c ss_on_rx_notify … bad property` в
  СВЕЖЕМ дампе станции.

### 4. Правки по вскрытым причинам

- (a) Пассивный UAS подписок — на уровне СТАНЦИИ (не только во время прогонов):
  SUBSCRIBE пакетов `event-list`/`dialog-info`/`presence`/`blf` → 200 с
  Contact станции (мимикрия расширяется, OPTIONS/прочее без изменений); иначе
  SSW_SRVM подписка пира живёт только внутри прогона, а NOTIFY запаздывает.
  По дампу №2 это КЛЮЧ к кейсу B: станция заходит в `ss_on_rx_notify` только
  как подписчик СВОЕЙ живой подписки (её SUBSCRIBE приходит на
  `u00sXXpXX@.159:5060` — trunk 02 в дампе №1, trunk 34 в дампе №2); пока
  отвечаем 405 — обработчик на станции не регистрируется и любой NOTIFY →
  500 «Unknown method» (90/90 в дампе №2). 200 обязаны приходить и вне
  прогонов стимула (п.4c о таймерах pjsip).
- (b) event-list NOTIFY — строго в диалоге принятой подписки пира: R-URI и
  назначение — `Contact:` из её SUBSCRIBE (`.133:5060`; в дампе №2 Contact
  trunk 34 — `.157:5060`, брать из фактического Contact), Call-ID/From/To-теги
  из диалога, CSeq монотонно, `Event: event-list`, тело — побайтовая копия
  триггеров res.md B (value len 137 при allowed 32; name
  `replace_category_from_redirection` len 33).
- (c) 408 из нового лога: ответ на SUBSCRIBE обязан уходить быстрее таймеров
  pjsip (UAS станции отвечает сразу, без ожидания живого клиента прогона).
- (d) Тесты: unit — станция отвечает 200 на SUBSCRIBE (формирование ответа,
  Contact, тег); unit/api — честность сводок после правки хука; сборка/тесты
  зелёные.

### 5. Приёмка и документация

- Критерий кейса B: в СВЕЖЕМ дампе станции появляются строки
  `ss_info.c ss_on_rx_notify: SSW_SRVM sub … bad property list: value … (len
  137, allowed 32)` и/или `bad property: name (…, len 33, allowed 32)` —
  программа ЗАШЛА в логику кейса.
- Журнал сессии `doc/task_27_plan_2.md` («симптом → причина → решение»,
  таблица логов, вердикты по H1–H4); при изменении контрактов — `doc/api.md`;
  строка статуса в `CLAUDE.md`.

# Журнал: правило комментирования кода (сверх плана, запрос пользователя)

## Выполненный пункт

Запрос: создать правило проекта о правилах комментирования кода; составить
его по факту — обследованием всех файлов проекта.

## Что сделано

- Обследованы все исходники (кроме `task2/`, `doc/plan_3.md`, генераций):
  `server/` (включая `server/sip/`, контроллеры, middleware), корневые
  `bridge_main.ts`/`e2e_runner.ts`, `tests/unit|api|e2e`, `doc/.probe_*.ts`,
  `public/index.html`. Собраны фактические конвенции: заголовки файлов блоком
  `//` с план-ссылками и строкой `related:` (вместо JSDoc `@fileoverview`),
  однострочный/многострочный JSDoc экспортов, `@param` только для значимых
  параметров (флаги — перечислением значений), комментарии «граблей» с
  формой «иначе …», поведение станции с пометкой «стенд», реестр дефектов
  `BUG-N`, отсылки в `doc/sip_rfc.md`/`doc/task_N_plan_2.md`, баннеры секций
  `// ----- имя -----`, пустые ветки `/* noop */`, русские имена `it(...)`
  в тестах, русские `ctx.step(...)` в раннере.
- Создан `.claude/rules/comment_style.md` — 7 разделов: общие нормы (язык,
  why-not-what, ссылки, типографика), заголовок файла, JSDoc экспортов,
  строчные комментарии, разделители секций, тесты и раннер, плотность.
  Все примеры процитированы 1-в-1 из кода проекта (с указанием файлов).
- Правило дополняет §8 свода `.claude/rules/ts_code_style.md` (не дублирует)
  и объявлено локальной политикой свода по его §9.

## Результат проверки критериев

- Проверка типов/тесты не затронуты (правится только markdown), код проекта
  не изменялся.
- Каждый тезис правила подтверждён цитатой из существующего кода — правило
  описывает фактическое состояние, новый код ему уже соответствует.

## Отклонения и расхождения

- `@fileoverview` свод допускает, но в проекте не применяется — правило
  закрепляет факт (заголовок `//`-строками), `@fileoverview` запрещён явно.
- Закоммеченный код в проекте не встречался — запрет зафиксирован
  превентивно.
- Плотность комментариев сознательно неравномерна (заголовки пула/раннера
  ~15–20 % строк, тонкие контроллеры ~5 %); правило фиксирует вилку, а не
  единый норматив.

## Дополнение (второй запрос пользователя): многрочная форма JSDoc

- §3 правила ужесточён: все JSDoc-комментарии — только многрочной формой
  (`/**` и `*/` с новых строк, текст с ` *`); однострочная `/** … */`
  запрещена явно как локальная политика проекта (сужает разрешение §8 свода
  по §9). Норма распространяется на все JSDoc без исключений: экспорты,
  методы, геттеры, private-поля.
- Заголовок `//`-блоком (§2), строчные `//` в теле (§4) и `/* noop */` (§4)
  норме не подлежат — это не JSDoc-документация.
- Расхождение: существующий код проекта (напр. `server/sip/state.ts`) местами
  использует однострочный JSDoc — под новую норму пока не переформатирован
  (по образцу п.13: переформатирование — отдельным проходом от правок).

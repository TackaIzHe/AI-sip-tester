# Журнал: разделение batch24 на регистрация/снятие (сверх плана, запрос пользователя)

## Выполненный пункт

Запрос: разделить один кейс регистрации/разрегистрации 24..47 (`batch24`,
doc/task_20_plan_2.md) на два: первый — абоненты регистрируются (основной),
второй — разрегистрируются (второстепенный; если не реализуется — не делать,
оставить заметку). Реализуемо в рамках одного процесса сервера — разделение
сделано, заметка о нереализуемой части ниже.

## Что сделано

- `e2e_runner.ts`: `case_8_batch_reg_unreg` разделён на два кейса реестра
  `CASES` (порядок значим для `test all`):
  - `batch24reg` — `case_8a_batch_reg` (основной, отчёт
    `case_8a_batch_reg_24_47`): регистрирует 24..47 (`REGISTER → 200` у
    каждого + состояние REGISTERED, ассерты по сырым сообщениям — без
    изменений) и ОСТАВЛЯЕТ регистрации живыми; чистый старт — прежние
    регистрации диапазона снимаются тем же пулом (иначе идемпотентный
    `register_subscriber` не отправил бы REGISTER и цепочка пуста);
  - `batch24unreg` — `case_8b_batch_unreg` (второстепенный, отчёт
    `case_8b_batch_unreg_24_47`): снимает оставленное (`200` на REGISTER
    expires=0 у каждого), снимает только фактически зарегистрированные
    (частичный FAIL кейса регистрации — не повод не чистить остатки); после
    снятия (успех/FAIL) пул закрывается и кэш сбрасывается.
- Механизм разделения — живой пул между прогонами: модульная переменная
  `batch_pool` в `e2e_runner.ts`, лениво создаётся `get_batch_pool()` прогоном
  case_8a и читается case_8b. Это сняло ограничение журнала п.20
  («`run_case` не хранит состояние между прогонами»): состояние — сам
  модуль раннера живущего процесса сервера (терминал, `POST /api/test_runs`,
  `test all` — один и тот же процесс, один `Journal`).
- `close_batch_pool()` (экспорт раннера) подключён в `shutdown()`
  `server/main.ts`: `quit`/SIGINT/SIGTERM снимают и «вислые» после case_8a
  регистрации диапазона (иначе они пережили бы процесс до expires станции;
  24 unregister'а могут не влезть в 3 с таймаут shutdown — хвост истечёт сам).
- Заметка о нереализуемом: снять регистрации из ДРУГОГО процесса нельзя —
  REGISTER expires=0 станция сопоставляет с binding по Contact того же UA
  (`server/sip/sip_ua_transport.ts`: порт Contact — эфемерный сокет
  транспорта; новый процесс = новый Contact = чужая binding). Поэтому
  case_8b без живого `batch_pool` (сервер перезапускался после case_8a)
  честно FAIL с этим текстом — это и есть «не получилось реализовать»
  часть запроса, второстепенность кейса фиксирована в его шапке и в
  вердикт-тексте case_8a.
- Синхронизация потребителей: `tests/api/test_runs.test.ts` (список id),
  `doc/api.md` (пример GET, тело POST, пример 400), `README.md` (команда
  терминала, таблица кейсов — две строки, структура), шапки
  `server/terminal.ts`/`e2e_runner.ts`, `CLAUDE.md` (статус + описания).
  Вкладка «Тесты» и `POST /api/test_runs` — без правок (читают
  `implemented_cases()`).

## Отклонения

- `batch24` (общий прогон пары) из реестра удалён — вместо него два id;
  парный сценарий полностью покрыт `test all` (кейсы идут подряд: reg →
  unreg закрывает пул) и vitest-файлом `tests/e2e/batch_24_47_reg_unreg.test.ts`.
- «Вислые» регистрации между case_8a и case_8b — ожидаемое поведение
  разделения (иначе второй кейс теряет объект снятия); страховки — case_8b,
  `close_batch_pool()` на shutdown и expires станции.

## Документация для будущих сессий

- Порядок кейсов в `CASES` значим: `batch24unreg` обязан идти сразу за
  `batch24reg` (в `test all` он закрывает живой `batch_pool`).
- Диапазон по-прежнему дублируется с vitest-файлом (`BATCH_FROM`/`BATCH_TO`
  в `e2e_runner.ts` и в `tests/e2e/batch_24_47_reg_unreg.test.ts`).
- Повторный `batch24reg` без снятия безопасен: чистый старт снимает свои же
  прежние binding тем же пулом; новый `batch24unreg` после снятия — FAIL
  («нет живого пула»), это ожидаемо.

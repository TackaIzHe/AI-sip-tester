# План тестов для воспроизведения утечки памяти в SIP-адаптере (pa_sip)

Без привязки к языку программирования. Документ описывает: критерии воспроизведения, окружение, измерительную методику и набор тест-сценариев по каждому кандидату из отчёта `res.md`.

---

## 1. Цель и определение «утечка воспроизведена»

**Цель:** для каждого места-кандидата (A–F из `res.md`) доказать или опровергнуть, что обработка конкретного сообщения оставляет неразблокированную память в процессе SIP-адаптера.

**Тест считается положительным (утечка воспроизведена), если выполнены ВСЕ условия:**

1. **Линейный рост:** RSS адаптера растёт линейно от числа отправленных стимулирующих сообщений (коэффициент корреляции R² > 0.95 на интервале ≥ 30 мин или ≥ 10 000 сообщений).
2. **Невозврат:** после прекращения стимуляции RSS не снижается к базовому уровню в течение ≥ 15 мин (отсечь отложенное освобождение/кэш аллокатора).
3. **Масштаб:** удельный прирост устойчив — X байт на сообщение стабилен (разброс < 20%) и **не plateau-ится** со временем (плато = ограниченный пул/кэш, а не утечка).
4. **Исключение легитимного роста:** число активных сущностей (транзакции, диалоги, подписки, RPC) в конце теста вернулось к фоновому уровню, а память — нет.

**Формула результата:** `утечка = ΔRSS / (N_сообщений − N_потерь)` [байт/сообщение]. Результат фиксируется в журнале теста.

## 2. Окружение и подготовка

### 2.1. Состав стенда
- **DUT:** АТС с уязвимой прошивкой (CORAL 17.1.13, pa_sip 3.402.0.100), конфиг максимально близкий к продакшену из трасс: 8 SIP-интерфейсов, транк на тестовый коммутатор, ~1000+ подписок BLF, подписки distinctive-ring (SSW_SRVM).
- **Генератор SIP-трафика:** любой — SIPp (сценарии XML), реплей pcap, или самописный UA на любой SIP-библиотеке. Требования: точный контроль тела/заголовков, темпа (msg/s), повторного использования src-порта, возможность шить битые сообщения (обрыв, мусор после Content-Length).
- **Монитор памяти:** опрос `/proc/<pid-адаптера>/status` (VmRSS, VmData, VmStk) и `/proc/meminfo` каждые 5–10 с с метками времени; опционально — jemalloc/tcmalloc profiling, если адаптер пересобран под них.
- **Захват:** pcap на зеркала SIP-порта — ВСЕГДА включён, для привязки момента роста к конкретному сообщению по timestamp.
- **Логи:** SIP trace level 5 на отдельный диск без ротации 20 МБ (главный урок из анализа: логи ротируются раньше, чем накапливается измеримый рост).

### 2.2. Обязательные метки в журнале
В момент старта/остановки каждой фазы стимула — маркер в лог монитора памяти и в tcpdump (`comment`-пакет/пустой UDP-датаграммар на служебный порт), чтобы три ряда (память/пакеты/лог) сшить по времени без привязки к языку.

### 2.3. Подготовка состояния DUT (общая преамбула всех тестов)
1. Загрузка конфигурации, ожидание полной готовности (стабильный RSS ≥ 5 мин, «прогретый» аллокатор).
2. Регистрация тестовых портов и установка фоновых подписок BLF/SSW_SRVM.
3. Замер базового RSS (30 мин покоя) — стартовая точка.
4. Фоновый «нормальный» трафик (звонки + NOTIFY по подпискам, ~тот же CPS что в `traces_normal_load`) — тестировать в условиях, близких к продакшену, т.к. утечка может проявляться только под нагрузкой.

## 3. Тест-сценарии по кандидатам

### T1 — NOTIFY с битым dialog-info (кандидат A, `blf.c : blf_on_rx_notify`)
**Стимул:** на каждую активную BLF-подписку присылать NOTIFY (Call-Id/CSeq в диалоге подписки, `Content-Type: application/dialog-info+xml`) с телами-вариантами ошибок:
- a) XML без элемента `<dialog>` (пустой `<dialog-info>`);
- b) `<dialog>` без `<remote><identity>`;
- c) тело не-XML (текст/JSON) при верном Content-Type;
- d) обрезанный XML (обрыв на середине тега);
- e) корректный XML + лишний Content-Encoding.

**Темп:** 1.5 NOTIFY/с на подписку (как в проде) × все подписки. **Длительность:** ≥ 30 мин (≥ 2700 сообщений на подписку).
**Ожидаемый сигнал утечки:** рост RSS прямо пропорционален числу битых NOTIFY; из лога — `body xml invalid/unexpected`.
**Дозимерение:** прогнать вариант (f) — корректные NOTIFY тем же темпом, чтобы отделить парсинг-ошибку от самого факта обработки NOTIFY.

### T2 — event-list NOTIFY oversized property (кандидат B, `ss_info.c : ss_on_rx_notify`)
**Стимул:** на подписку SSW_SRVM (event-list, «distinctive_ring») слать NOTIFY с телом `application/simple-list+xml`, содержащим N свойств, где:
- a) `value` длиной 137 байт (XML-сущности `&quot;` включены) при лимите 32 — как в логах;
- b) `name` длиной 33 байта (`replace_category_from_redirection`);
- c) гибрид: много свойств по 137 байт в одном NOTIFY (эмулируем сотни префиксов).

**Темп:** 1 NOTIFY/с, внутри каждого 100–1000 свойств (вариант c — критический: проверяем накопление свойств внутри ОДНОГО сообщения). **Длительность:** ≥ 30 мин.
**Замер格外:** отдельно ΔRSS на «битое свойство» (сообщение с 1 плохим свойством) и на сообщение с 500 плохими — утечка внутри цикла парсинга свойств даёт линейность по свойствам, а не по NOTIFY.

### T3 — дубли подписок (кандидат C, `mod_pa_subscription : sub_create_uac`)
**Стимул:** каждые T секунд переотправлять полную конфигурацию подписок (создание BLF/SSW_SRVM подписок, которые уже активны) — эмуляция повторного `Total config` от app без удаления старых подписок. Цикл: отправить конфиг → дождаться `already active` → пауза → повторить.
**Темп:** полный цикл раз в 2–5 мин (как при рестартах app), сотни дублей за цикл.
**Ожидаемый сигнал:** ΔRSS на цикл дублей; из лога — `sub_create_uac: BLF sub XXXX already active`.
**Контроль:** после теста удалить все подписки и пересоздать — проверить, освобождается ли память при teardown (утечка «навсегда» vs «до переконфигурации»).

### T4 — 401 с неизвестным realm (кандидат D, `sip_auth_client.c`)
**Стимул:** тестовый провайдер-коммутатор отвечает 401 на исходящие REGISTER/OPTIONS/SUBSCRIBE адаптера с `WWW-Authenticate: Digest realm="GUmvd"` (realm отсутствует в конфиге адаптера). Цикл: регистрация → 401 → адаптер ретраит по refresh-таймеру.
**Длительность:** ≥ 24 ч (медленная утечка: в логах ~50 ошибок на 4-мин окно, но объект `tdta` на каждую).
**Альтернатива (быстрее):** инициировать изнутри частые исходящие запросы (OPTIONS keepalive каждый порт) под 401.
**Ожидаемый сигнал:** медленный линейный рост; из лога — `Unable to set auth ... can not find credential`.

### T5 — «не от транка»: flood чужих REGISTER/SUBSCRIBE (кандидат F, `mod_pa_transit_ab`)
**Стимул:** с «чужого» IP/порта, никогда не настроенного как транк, слать:
- a) REGISTER cseq=1 (повторно, как сканер);
- b) SUBSCRIBE cseq=1 на несуществующий контакт;
- c) INVITE cseq=1 c неизвестным From.

**Темп:** 1–5 msg/s на каждый вариант (в проде ~280 за 4 мин — начать с прод-темпа). **Длительность:** ≥ 1 ч.
**Контроль:** после flood'а — пауза 15 мин (ответы 4xx уходят, транзакции завершаются → утечки быть не должно; если RSS не вернулся — утечка reject-пути).

### T6 — невалидные IPC-сообщения subscribe (кандидат E, `ipc.c`)
**Стимул:** (нужен доступ к IPC-разъёму app↔адаптер) отправка IPC-сообщения `subscribe` (type 54) с заведомо невалидными полями — эмуляция бага конфигурации.
**Темп:** 10–100/с, ≥ 10 000 сообщений.
**Сигнал:** рост RSS на каждое `error 70004 (PJ_EINVAL)`.

### T7 — resolver-шторм (косвенный кандидат, `ext_domain_resolver`)
**Стимул:** исходящие SIP-сообщения на доменные имена (не IP) с подменой DNS-ответа (long TTL / NXDOMAIN / таймаут), чтобы резолв-запросы намеренно подвисали; параллельно — штатный трафик 35 res/с.
**Сигнал:** рост RSS/памяти `mod_rdn` при накоплении ожидающих запросов; проверка, что ответ/таймаут резолва освобождает очередь.

### T8 — комбинированный «продакшен-реплей» (интеграционный)
**Стимул:** воспроизвести картину целиком: нормальная нагрузка + фоновый поток битых dialog-info NOTIFY (1.5/с) + изредка битые event-list NOTIFY + чужие REGISTER cseq=1.
**Длительность:** soak ≥ 12–24 ч с непрерывным мониторингом RSS всех процессов (`app`, `pa_sip`, `mod_rdn`).
**Цель:** дождаться деградации до OOM-состояния (признак-маркер: `malloc failed` в новых процессах, `Killed`). Этот тест подтверждает гипотезу «совокупная утечка из A/B+F» как первопричину краха.

## 4. Методика проведения каждого теста (единый шаблон)

| Шаг | Действие |
|---|---|
| 0 | Фиксация версии прошивки/сборки, снимок конфигурации, снапшот состояния сущностей (число транзакций/диалогов/подписок из логов) |
| 1 | Преамбула из §2.3, базовый RSS |
| 2 | Фаза покоя 10 мин (контроль шума) |
| 3 | Фаза стимула (по §3: темп, длительность, вариант тела) |
| 4 | Фаза наблюдения 15 мин без стимула |
| 5 | Снятие снапшота памяти и сущностей, остановка pcap, разбор |
| 6 | **A/B проверка:** повторить тот же стимул с «исправленным» сообщением (корректный XML / корректный размер свойства / известный realm / известный транк). Разница ΔRSS(bad) − ΔRSS(good) = вклад error-пути |

**Правила чистоты:** один тест = один кандидат; между тестами — полный рестарт адаптера и 15-мин стабилизация; порядок тестов рандомизировать; каждый тест ≥ 2 повтора.

## 5. Диагностика при подтверждении утечки

1. Взять core-dump адаптера по сигналу (или снапшот heap при RSS = базовый + N МБ).
2. Диффом двух снапшотов (начало/конец стимула) выделить объект, растущий пропорционально числу сообщений; по содержимому (строки тела NOTIFY, realm, subref) привязать к функции-аллокатору.
3. Если есть сборка с символами — прогон под massif/heap-profile на минимальной версии стимула (1000 сообщений) для точной стековой трассировки.
4. Проверить, что ошибка освобождается на нормальном пути (вариант f в T1) — это подтверждает «утечка именно на error-return».

## 6. Приоритет и очередь запуска

| Приоритет | Тест | Кандидат | Почему |
|---|---|---|---|
| 1 | T1 + контрольный f | A | Максимальная частота в проде (~50 МБ/ч при 10 КБ/сообщение) |
| 2 | T2 (особенно в) | B | Утечка×сотни свойств×refresh — второй по темпу |
| 3 | T5 | F | Дешёвый в постановке, высокий темп |
| 4 | T3 | C | Видим только на переконфигурации |
| 5 | T4 | D | Медленный, но бессмертный (realm `GUmvd` живёт в проде) |
| 6 | T6 | E | Требует IPC-доступа |
| 7 | T7 | resolver | Только при подтверждённой деградации mod_rdn |
| 8 | T8 | всё | Финальная связка до OOM |

## 7. Что записываем в отчёт по каждому тесту
- сборка DUT, дата, длительность фаз;
- таблица: время, RSS, счётчик отправленных стимулов, счётчик соответствующих ошибок в логе адаптера;
- ΔRSS/сообщение, R² линейности, факт возврата/невозврата RSS;
- вердикт: утечка подтверждена / опровергнута / требует heap-диффа.
